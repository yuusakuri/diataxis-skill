# 評価

スキルを読み込んだエージェントが、スキルの言うとおりに振る舞うかを確かめます。

`claude plugin eval`の形式です。各caseはプロンプトと採点器（grader）の組で、採点器はどれも`SKILL.md`が求める挙動を1つずつ述べたものなので、採点器の失敗はスキルと実際の動作との差を意味します。

## 実行する

```bash
claude plugin eval .
```

各caseは、スキルを読み込んだ実行（with）と読み込まない実行（baseline）の両方を既定3回ずつ行い、その差を`Δ`として報告します。`Δ`がほぼ0のcaseは、スキルが寄与していないcaseです。

1つのcaseだけを安く回すには、片方の腕だけを1回実行します。

```bash
claude plugin eval . --case <case-name> --runs 1 --ablation none
```

結果は`evals/results/<timestamp>/`に出ます。gitには入れません。

## 構成

```text
evals/
└── diataxis/               # スキル名。caseはこの下に置きます
    └── <case>/
        ├── prompt.md       # frontmatter: 実行条件 / 本文: プロンプト
        ├── case.yaml       # fixturesの読み取り許可
        ├── fixtures/       # プロンプトが対象とするドキュメント
        └── graders/        # 採点器。1ファイル1項目
```

caseは`evals/`直下ではなくスキル名のディレクトリに置きます。スキルが増えたときに、どのcaseが何を測っているかが混ざらないようにするためです。

`claude plugin eval`のeval用ディレクトリは`skills/`の中には置けません。スキルの同梱ファイルとして読み込まれてしまうためです。

## caseが見ているもの

| case | 見ているもの |
| --- | --- |
| `tutorial-or-how-to` | TutorialとHow-toの境界。前提条件があってもTutorialとして扱えること |
| `reference-keeps-examples-and-warnings` | Referenceから使用例、必須条件、警告を削らないこと。通しの手順だけを外に出すこと |
| `keeps-domain-first-layout` | 機能している製品別の構成を、モード別ディレクトリへ置き換えないこと |
| `splits-only-what-is-mixed` | 実際に混ざっているページだけを分割すること |
| `no-empty-scaffolding` | 内容のないモードのディレクトリ、索引の行、雛形ページを作らないこと |

## 採点器を書く

モデルが元から持っている知識ではなく、スキルが求める挙動を採点器にしてください。

「4つのモードをすべて挙げる」はスキルを読み込まなくても通るので、何も測っていませんし、失敗しようもありません。baselineとの差がそれを可視化します。

`SKILL.md`や`references/`に載っている例と同じ題材を使わないでください。例の再現を測ることになり、一般化しているかどうかが分からなくなります。

`tool_used`で`Skill`を見る採点器は、スキルが起動したかどうかの表示であって、点数には入りません。判定は出力の中身で行います。

Diátaxisに書かれていない分類規則をcaseにしないでください。このスキル独自の判定を正解として固定すると、evalがDiátaxisではなく独自体系を守るものになります。

出力が長いcaseでは、機械的な確認は`regex`採点器にしてください。LLM採点器は実行ごとに判定が割れます。1つの採点器で複数のファイルを同時に見ると、さらに割れます。

プロンプト、入力、採点器は英語です。入力はエージェントが分析する対象そのもので、採点器の文面は判定モデルが読むため、翻訳すると測っているものが変わります。
