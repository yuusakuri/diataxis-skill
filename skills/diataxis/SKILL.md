# Diátaxis

ドキュメントの問題の多くは、文章ではなく分類の問題です。

1つのページが2種類の読者を同時に相手にしようとして、どちらの役にも立たなくなっています。

Diátaxisは、読者がそのページを開いた時点の必要によって、ドキュメントを4つのモードに分けます。

このスキルでの仕事は、ページが応える読者の必要を特定し、その必要に合う内容、書き方、配置にすることです。

## モードを判断する

2つの問いで決まります。

主題ではなく、読者がそのページを開いた時点の状況を問います。

1. これは行動（すること）を扱うのか、認識（考えること）を扱うのか。
2. 技能の習得（学んでいる状態）に応えるのか、技能の適用（作業している状態）に応えるのか。

| 扱うもの | 応える状況 | モード |
| --- | --- | --- |
| 行動 | 技能の習得 | Tutorial |
| 行動 | 技能の適用 | How-to guide |
| 認識 | 技能の適用 | Reference |
| 認識 | 技能の習得 | Explanation |

ページが応える主たる読者ニーズを1つ定めてください。

異なる読者ニーズに応える内容が同じページに実際に混ざっているときは、分割して互いにリンクします。それが答えであって、妥協ではありません。

読者や利用状況が読み取れないときは、周辺のドキュメントの構成や依頼の内容から目的を確かめます。判断材料が足りないことを、モードの混在と取り違えないでください。

## 各モードが読者に負うもの

| モード | 読者の状況 | ページの役割 | してはならないこと |
| --- | --- | --- | --- |
| Tutorial | 対象の技能を習得している最中 | 明示した開始条件から、案内に沿って期待した結果まで確実に届ける | 分岐する、代替案を論じる、選択肢を並べる |
| How-to guide | 作業中で、何が欲しいか分かっている | 現実の問題を解決する経路を示し、状況の違いを扱う | 教える、説明する、網羅する |
| Reference | 作業の途中で、今すぐ事実が要る | 正確で、完全で、退屈に、仕組みを記述する | 一連の作業手順を案内する、説得する、理由を論じる |
| Explanation | 理解しようとしていて、キーボードの前にいない | 理由を論じ、考えを結びつけ、代替案とトレードオフを認める | 指示する、目録を作る |

## 既存のドキュメントを扱う

何かを提案する前に、ページを読んでください。

1ページずつ、どの読者に向けたもので、その読者は何をしていて開いたのかを言葉にします。

それを言えないページが、最初に手を付けるべきページです。

どの行から判断したのかを示してください。著者があなたではなく根拠に反論できるようにするためです。

読者が何を必要としているかは、あなたが下して擁護する判断です。測定結果のように見せてはいけません。

見つけたものは、次のように扱います。

1. モードを言えないページは、判断の軸を当てて主たる読者ニーズを定めます。
   2つの必要が本当に混ざっているなら、それは2つのページです。
2. 役割が混ざったページは、異質な部分を切り出して本来のモードのページへ移し、リンクを残します。
   圧倒的に多いのは、ReferenceやExplanationに一連の作業手順が吸収されている場合です。手順を探す人が見ない場所に、手順が隠れています。
3. あるモードが無いことは、それを必要とする読者がいるときだけ不足です。
   その読者が何を求めて来るはずかを伝え、実際に現れるまでは不足のままにしておきます。

段階的に進めてください。

ドキュメントは並べ替えている最中にも読まれています。1ページずつ動かし、リンクを生かしておきます。

大きな構成を一斉更新なしに扱う方法は`references/how-to-restructure.md`にあります。

## モードとディレクトリ

モードはページの目的と書き方を決める分類であって、特定のディレクトリ構造を要求するものではありません。

既存の情報設計があるなら、それを保ったまま各ページのモードを明確にします。製品別やサービス別に分かれた構成は、それ自体が問題ではありません。ディレクトリを動かさずに解ける問題を、ディレクトリを動かして解かないでください。

既存の構造がない小規模な新規ドキュメントでは、次の構成を候補として使えます。

| パス | 置くもの |
| --- | --- |
| `tutorials/` | 番号付きの学習用の文書。通常はごく少数 |
| `how-to/` | 実際の作業ごとに1ファイル。「〜する方法」と題する |
| `reference/` | 記述対象の構造をそのまま映したページ |
| `explanation/` | 主題ごとに1ファイル。問いか主題で題を付ける |

対応する文書が存在しないモードのディレクトリは作りません。

索引は、複数のページを案内する必要が生じた時点で作ります。索引やランディングページ自体は案内であって、4つのモードのどれかに割り当てるものではありません。

テンプレートが`assets/templates/`にあります。

読者は名前を頼りに動くので、2つの命名規則が大きな比重を占めます。

How-to guideは読者の目的で題を付けます。「APIキーを更新する方法」であって、「rotateコマンド」ではありません。

Explanationは問いか主題で題を付けます。作業のようには付けません。

## 範囲

渡されたものを整理してください。

docsフォルダを整理してほしいという依頼は、無いページを書いてほしいという依頼ではありません。

体裁を揃えるためにページを作らないでください。

中途半端に埋まった4つのモードは、良いモード2つに勝りません。空の`tutorials/`は存在しない学習用の文書があるように見せますし、枠を埋めるために書かれたTutorialは、誰も学びたいと言っていないことを教えます。

あるモードが無く、それを求める読者がいると考えるなら、その読者が何を求めて来るはずかを伝えてください。

書くかどうかは著者が決めます。

## モードに沿って書く

書き始める前に、そのページがどのモードで、なぜそうなのかを言葉にしてください。

その一文が書きにくいなら手を止めます。そのページはまだ1つのものになっていません。

Tutorialは一人称複数で書き（「〜を作ります」）、具体的な成果を最初に約束し、どの手順にも読者が照合できる目に見える結果を持たせます。

開始条件を最初に明示します。前提条件があってもTutorialとして成立します。成立しなくなるのは、その前提が書かれていないときです。

その手順に必要な以上の説明はせず、リンクで外へ出します。読者は最後まで終えて、うまくいったと感じられなければなりません。

How-to guideは道具ではなく問題から始めます。

読者に能力があることを前提にし、現実にぶつかる状況の違いを扱います（「マネージドインスタンスの場合は代わりに…」）。経路の上にないものはすべて省きます。

Referenceは簡素に、一貫させます。

何をすべきかではなく、何であるかを述べます。コードやAPIの構造を映す形にして、どこに何が書いてあるかを読者が予測できるようにします。ここでは文章の質より一貫性が重要です。

使用例、パラメータ、戻り値、制約、必須条件、禁止事項、警告、エラー、互換性は、いずれもReferenceの内容です。読者が正しく使うために必要な事実なので、削らないでください。

Referenceが書かないのは、タスクを完了するまでの一連の作業手順です。それはHow-to guideの仕事で、Referenceからはリンクします。

Explanationは問いで範囲を区切ります（「なぜXなのか」「YとZはどう噛み合うのか」）。

意見、経緯、代替案を出してかまいません。それがあるからこそ、形容詞の付いたReferenceではなくExplanationになります。

モードごとの詳しい指針と分割の例は`references/four-modes.md`にあります。ページの置き場所が決めにくいとき、別のモードへ書き換えるときに読んでください。

## 適用しない文書

Diátaxisは読者のために書かれたドキュメントを対象とします。

文書の形式そのものに独立した意味がある成果物には適しません。アーキテクチャ決定記録、プロダクト要求仕様書、RFC、変更履歴がこれにあたります。決定に至った背景、承認に必要な項目、提案の手続き、時系列という形が、その文書を役立たせています。4つのモードに押し込むと、その構造が失われます。

名称だけで対象外にしないでください。運用手順書やRunbookと呼ばれていても、特定の目的を達成するために読者が実行する手順であれば、How-to guideです。中身を読んで判断します。

ただし、その文書の形そのものが役割を果たしているなら、モードの名前が何であれ、ページはそのままにします。障害対応のチェックリストがその例です。上から順に実行できること、時刻で区切られた区分、エスカレーション先が、緊迫した場面での有用性を作っています。題の付け方を含めて、How-to guideの作法を当てはめないでください。

対応するスキルがプロジェクトにあるなら、そちらを使い、ドキュメントの構成には手を付けないでください。

## 危険信号

| 見かけるもの | 実際に起きていること |
| --- | --- |
| モードを言えないページ | 1つのファイル名をかぶった2つのページ |
| 実態がオプションの目録になっている「はじめに」 | 教えるのをやめたTutorial |
| 通しの作業手順が書かれたReferenceの項目 | 誰も探しに来ない場所に手順が隠れている |
| 指示で終わるExplanation | そこにあると思われていない手順は、誰も保守しない |
| 空のモードディレクトリが4つ | 構造を作ることが目的になっている。空の`tutorials/`は、`tutorials/`が無いより悪い |
| ページを読まない再編成 | 分類は読者が内容から何を必要とするかの問題で、ファイル名からは分からない |
| 動いている構成の全面的な置き換え | モードを明確にする作業が、ディレクトリを動かす作業にすり替わっている |
