# 4つのモードの詳細

ページの置き場所が決めにくいとき、あるモードから別のモードへ書き換えるときに読んでください。

判断の軸は`SKILL.md`にあります。ここには詳細と具体例を置きます。

書き始める前に、そのページがどのモードで、なぜそうなのかを言葉にしてください。その一文が書きにくいなら手を止めます。そのページはまだ1つのものになっていません。

以下は各モードが何に応えるかであって、見出しの雛形ではありません。必要のない節を体裁のために足さないでください。

## Tutorial

読者は対象の技能を習得している最中で、自分が何を知るべきかをまだ知りません。

語彙を持っていないので、何が欲しいかを言葉にできません。与えるべきものは、うまくいったという経験です。

完全な初心者であることは条件ではありません。すでに他の部分を使っている読者に、新しい領域を習得させるTutorialもあります。

- 一人称複数で書きます（「〜を作ります」）。読者を一人にしないための書き方です。
- 具体的な成果を1つ約束し、最初に伝えて、それだけを届けます。
- 開始条件を明示します。
  前提知識や事前の設定があってもかまいません。書かれていない前提だけが、Tutorialを壊します。
- どの手順にも目に見える結果を持たせます。
  「次のように表示されます」はTutorialの要となる一文です。読者が道を外れていないことを自分で確認できます。
- 道筋は1本だけにします。
  「こうすることもできます」も、条件分岐も、代替案も書きません。選択肢を出すたびに、読者が迷う機会が増えます。
- 説明は最小限にします。
  読者が理由を知りたくなる箇所には、Explanationへのリンクを置いて先へ進みます。
- 明示した開始条件から、毎回必ず最後まで動くようにします。
  手順7で失敗するTutorialは、無いよりも悪いものです。このプロジェクトは信用できないと教えてしまいます。

Tutorialは維持費が最も高く、ほとんどのプロジェクトで数を絞るべきものです。

動くもの1本が、腐った5本に勝ります。

## How-to guide

読者は作業中の、能力のある人です。

目的があり、現実の込み入った状況に置かれています。

- 読者の目的で題を付けます。「APIキーを更新する方法」であって、「rotateコマンド」ではありません。
- 道具ではなく問題から始めます。
  仕組みは手段であって主題ではありません。
- 状況の違いを扱います。
  現実は一様ではないので、「マネージドサービスを使っている場合は代わりにXをします」のように書き分けます。
- 教えません。
  読者はシステムを学びたいのではなく、作業を終わらせたいのです。
- 網羅しません。
  How-to guideは経路であって地図ではありません。網羅はReferenceの仕事です。

最も多い失敗は、道具を中心にしたガイドを書くことです。

「exportコマンドの使い方」と題されると、そのコマンドが自分の問題を解決するのかどうかを、読者が自分で考える羽目になります。

## Reference

読者は作業の途中で、事実を1つ必要としています。

来て、1つ取って、去ります。

- 仕組みを記述します。
  何であるかを述べます。書かないのは、タスクを完了するまでの一連の作業手順です。
- 正しく使うために必要な事実は残します。
  使用例、パラメータ、戻り値、制約、必須条件、禁止事項、警告、エラー、互換性は、いずれもReferenceの内容です。`--force`が既存のファイルを消すという警告は、指示ではなく事実です。
- 記述対象の構造をそのまま反映させます。
  コードにモジュールがあるなら、Referenceにもモジュールがあります。読者がどこを見ればよいか予測できるようになります。
- 何よりも一貫させます。
  どの項目も、同じ順序、同じ見出し、同じ粒度で書きます。読者は形を一度覚えれば、あとは速く読めます。
- 簡素にします。
  Referenceは退屈でかまいません。ここでの個性は、読者が探す速度を下げます。
- 可能ならソースから生成します。
  手書きのReferenceは実態からずれていきます。間違ったReferenceは、無いReferenceより悪いものです。

「Referenceに命令形を書いてはならない」という規則ではありません。

取り除くのは、目的から完了までを案内する手順の連なりです。1つの項目を正しく使うための警告や必須条件を削ると、読者は事実の半分だけを持って帰ることになります。

## Explanation

読者は理解しようとしていて、おそらくキーボードの前にいません。

- 問いか主題で範囲を区切ります。「なぜデプロイは不変なのか」「キャッシュと無効化はどう噛み合うのか」のように書きます。
- 理由を論じます。
  経緯、制約、トレードオフ、退けた案とその理由を書きます。
- 意見や複数の見方を出してかまいません。
  4つのモードのうち、それが正しいのはここだけです。
- ものごとを結びつけます。
  Explanationは、他の3つのモードが前提としている理解の枠組みを、読者が作る場所です。

Explanationが無いとき、その代償は同じ推論の反復として現れます。コードレビューで、障害の振り返りで、誰も記録しなかった決定をめぐる議論で、同じ話が何度も繰り返されます。

その反復が実際に起きているなら不足です。起きていないなら、まだ不足ではありません。

## 4つの取り違え

| 取り違え | 症状 | 対処 |
| --- | --- | --- |
| Tutorial ↔ How-to guide | 能力を前提とした「はじめに」、あるいは基礎から教えるHow-to guide | 読者が自分の欲しいものを分かっているかを問う。分かっているならHow-to guide |
| Reference ↔ How-to guide | 通しの作業手順が書かれたReferenceの項目 | 手順をHow-to guideへ移し、項目からリンクする。警告や必須条件は項目に残す |
| Explanation ↔ Reference | APIの記述の中に埋もれた理由の議論 | Referenceは何であるかを述べる。論拠は外へ出す |
| Explanation ↔ How-to guide | 番号付きリストで終わる論説 | 分割する。手順が、それを必要とする人から隠れている |

## 分割の例

`docs/caching.md`という1つのファイルが4つの役割を担っている場合を考えます。

| 書かれている内容 | 本来のモード |
| --- | --- |
| オリジンが遅く、トラフィックに波があるためキャッシュを置いている | Explanation |
| CDNのみの構成も検討したが、無効化の遅延が許容できず退けた | Explanation |
| 有効にするには`CACHE=1`を設定してワーカーを再起動する | How-to guide |
| オプションと既定値の表 | Reference |
| 最初のキャッシュ付きエンドポイントを作る手引き | Tutorial |

これを4つのファイルに分けると、それぞれが1種類の読者を想定したページになります。

| ファイル | 内容 |
| --- | --- |
| `docs/explanation/why-we-cache.md` | なぜ存在するのか、何を退けたのか |
| `docs/how-to/enable-caching.md` | 「サービスでキャッシュを有効にする方法」 |
| `docs/reference/cache-options.md` | オプションの表 |
| `docs/tutorials/first-cached-endpoint.md` | 最後まで通る学習用の文書 |

何も削っていません。

それぞれの内容が、その読者のいる場所へ移っただけです。

ここで示したパスは、モードごとのディレクトリを持つ構成の場合です。プロジェクトの情報設計が別の形なら、分けた4つはその形の中に置きます。分けることが目的であって、このパスに合わせることが目的ではありません。

分割は、複数の読者ニーズが実際に混ざっているときの対処です。手順が主でその前に一段落の背景があるだけのページは、How-to guide 1枚のままでかまいません。
